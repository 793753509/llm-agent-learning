# Day 08：用五个测试用例，检查资料找得对不对

> 今天给 Day 05 的检索器批作业：最多返回一块和两块资料，成绩怎样变化？
> 先认清测试用例、被测程序和报告，理解三个指标在看什么，再从 R4 手算到平均分。全程不调用模型。

## 1. 为什么一次问答成功还不够？

“周末几点关门？”能找到资料，换成“WLAN 怎么用？”就可能失败。
我们需要一组固定输入，检查正常问题、不同措辞、需要多块证据和原文没有答案的情况。

这与写测试用例相似：先准备输入和预期，再执行程序，最后核对结果。
这里先给每道题算分，描述“有没有命中、找全了几成、第一条正确资料排第几”。

## 2. 五道题和报告分别从哪来？

| 文件 | 谁提供，做什么 |
|---|---|
| [datasets/rag_cases.json](datasets/rag_cases.json) | 人工编写的五个测试用例：问题和应该找到的资料编号 |
| [Day 05 原文](../day05/knowledge/) | 人工编写的自习室资料，被检索器搜索 |
| [eval_retrieval.py](eval_retrieval.py) | 执行程序，调用 Day 05 的检索函数并计算分数 |
| `reports/lexical-k1.json`、`lexical-k2.json` | 上述程序运行后生成的报告，再次运行会更新 |

`cases` 表示用例；`lexical` 表示按相同词或字匹配的**关键词检索**；`k1` 表示每题最多返回一块。
报告名称用来区分“用哪种方法、最多取几块”，不是一个模型名称。

```text
人工写的题目与标准证据 + 人工写的原文
                    ↓
        程序逐题检索，得到实际结果
                    ↓
         与标准证据比较并计算分数
                    ↓
             程序保存 JSON 报告
```

标准证据提前由人确认，实际搜索结果与分数由程序计算。
直接修改报告里的分数不会改善检索，改过实现或输入后应重新运行。

## 3. 先看题目和原文

| 题号 | 问题 | 人工标注的标准证据 |
|---|---|---|
| R1 | 周末几点关门？ | `hours.md#1`：周末时间 |
| R2 | wifi 免费吗？ | `services.md#2`：网络说明 |
| R3 | WLAN 怎么用？ | `services.md#2`：网络说明 |
| R4 | 工作日和周末分别几点关门？ | `hours.md#2` 与 `hours.md#1` |
| R5 | 火星今天多少度？ | 空列表：原文没有答案 |

`hours.md#1` 是 Day 05 按空行切出的第一块，编号不是搜索排名。
每条用例的 `question` 是输入，`relevant_chunk_ids` 是标准证据，`purpose` 说明为什么出这道题，不参与评分。

**有答案题指原文里有依据，不代表检索器已经找到了。** 因此 R3 搜索失败仍要计 0 分；R5 则单独统计。
修改原文或切块方式后，需要重新审核标准编号；程序只能检查编号是否存在，不能替人确认标注是否正确。

## 4. 三个指标分别在看什么？

缩写记不清时，可查 [课程词汇表：评估与测试](../GLOSSARY.md#evaluation)。

用例提前标好了哪些资料是正确的。检索器返回结果后，我们从三个角度与标注比较：

| 指标 | 关注的问题 |
|---|---|
| Hit（命中） | 有没有找到正确资料？ |
| Recall（召回率） | 应该找到的正确资料，找全了多少？ |
| RR（Reciprocal Rank，倒数排名） | 第一条正确资料排在第几位？ |

先看每道有答案题的计算规则：

- **Hit**：至少找到一块正确资料记 1，一块都没找到记 0。
- **Recall**：找到的正确资料块数 ÷ 用例标注的正确资料块数。例如应该找到两块，只找到一块，得分就是 1/2＝0.5。
- **RR**：1 ÷ 第一条正确资料的排名。排第 1 得 1，排第 2 得 0.5；没有找到正确资料得 0。它只看第一条正确资料的位置。

`@k` 表示只检查返回结果的前 k 条。例如 RR@2 中，正确资料即使排在第 3，也记 0。
**多道题的 RR 取平均，就是 MRR（Mean Reciprocal Rank，平均倒数排名）。**

这些指标评价检索结果是否命中、是否完整、排序如何；它们不直接评价最终生成的回答是否正确。

## 5. 运行两次，先观察 R4

从项目根目录运行：

```bash
uv run python -m day08.eval_retrieval --top-k 1
uv run python -m day08.eval_retrieval --top-k 2
```

`top-k` 是每题**最多**返回几块，不是必须返回几块。当前检索器会先丢掉零分块，因此 k=2 也可能返回零块。

程序先打印题目文件、原文目录和检索方法，再逐题打印结果。R4 的关键输出为：

```text
# k=1：只找到工作日块
R4 工作日和周末分别几点关门？ -> ['hours.md#2']

# k=2：找到工作日块、周末块
R4 工作日和周末分别几点关门？ -> ['hours.md#2', 'hours.md#1']
```

两份成绩单分别保存到 [k=1 报告](reports/lexical-k1.json) 和 [k=2 报告](reports/lexical-k2.json)。
它们包含“应该找到的、实际找到的、每题分数、平均分”。

## 6. 用 R4 手算三个指标

把工作日块记为 A，周末块记为 B。R4 应该找到 A、B，k=1 实际只返回 A，k=2 返回 A、B。

| 指标 | k=1：A | k=2：A、B |
|---|---|---|
| Hit@k | 1 | 1 |
| Recall@k | 1÷2＝0.5 | 2÷2＝1 |
| RR@k | 1÷1＝1 | 1÷1＝1 |

R4 多找到 B 后资料更完整，所以 Recall 提高；原来就已命中，且第一名正确，所以 Hit、RR 不变。

再假设返回顺序是 X、A，X 是无关块：Hit@2＝1，Recall@2＝0.5，RR@2＝1/2＝0.5。
这时仍然命中一块，但第一条正确资料排得更靠后，所以 RR 降低。

## 7. 平均分是怎样得到的？

下面箭头表示 k=1 → k=2。平均只计算 R1～R4 四道有答案题：

| 用例 | Hit | Recall | RR |
|---|---|---|---|
| R1：周末时间 | 1 → 1 | 1 → 1 | 1 → 1 |
| R2：wifi | 1 → 1 | 1 → 1 | 1 → 1 |
| R3：WLAN，两次没找到 | 0 → 0 | 0 → 0 | 0 → 0 |
| R4：一块变两块 | 1 → 1 | 0.5 → 1 | 1 → 1 |

```text
k=1
平均 Hit    = (1 + 1 + 0 + 1)   / 4 = 0.75
平均 Recall = (1 + 1 + 0 + 0.5) / 4 = 0.625
MRR@1       = (1 + 1 + 0 + 1)   / 4 = 0.75

k=2
平均 Hit    = (1 + 1 + 0 + 1)   / 4 = 0.75
平均 Recall = (1 + 1 + 0 + 1)   / 4 = 0.75
MRR@2       = (1 + 1 + 0 + 1)   / 4 = 0.75
```

注意 Recall 是先给每道题算比例，再平均，不是把全部题的块数合并后相除。
Hit=0.75 表示四道中三道至少命中一块，不代表三道都找全。
以上基于当前五题和原文；修改后以重新运行结果为准。

R5 的标准证据为空，Recall 分母会为零。本课约定将无答案题单独统计：
`returned_candidate_on_unanswerable` 表示“有没有返回候选资料”。
当前 R5 会因“天”字匹配到预约说明，所以值为 true，但预约说明不能回答火星温度。
这只能说明返回了无用候选，今天没有调用模型，无法据此判断模型是否会编造回答。

## 8. 与报告里的字段对上

打开 k=1 报告，在 `cases` 找 R4，评分相关字段是：

```json
{
  "id": "R4",
  "relevant_chunk_ids": ["hours.md#1", "hours.md#2"],
  "retrieved": ["hours.md#2"],
  "hit": 1.0,
  "recall": 0.5,
  "rr": 1.0
}
```

`relevant_chunk_ids` 是预期，`retrieved` 是实际返回，下面是刚才手算的分数。
报告顶部 `dataset`、`knowledge`、`retriever` 说明题目、原文和被测函数；`generated_at` 是本次生成时间。
`answerable_count=4` 是平均分母，`mean.rr` 就是 MRR@k。

读代码按 `main → evaluate → metrics`：入口运行评估并保存，evaluate 逐题检索并求平均，metrics 给一道题打分。
核心 Recall 计算是：

```python
found = set(selected) & relevant
recall = len(found) / len(relevant)
```

集合交集找出“返回结果中属于标准证据的编号”，去重后再计数；同一块返回两次只能算一块。

## 9. 真实项目里一般怎么做？

例如内部制度助手，先从常见用户问题和真实失败中选一小批题，由熟悉制度的人标出支持回答的原文。固定资料版本与题目，修改检索后重跑，对比具体失败项。

通常还会另测生成：证据进了 Prompt 吗、回答受原文支持吗、引用对吗、资料不足时是否说明不知道？检索分数与回答质量分别看。
保留一些未用于调参的新题，避免只对已经看过的用例表现好。

本次 k=2 补齐了 R4，但没解决 R3；R1 还多拿了无关工作日块。不能只因平均 Recall 提高就认定整个系统更好。

## 10. 用门槛判断一次评估是否通过

```bash
uv run python -m day08.eval_retrieval --top-k 1 --min-recall 1
```

这要求平均 Recall 至少为 1。当前只有 0.625，程序先保存报告，再提示“未达到本次设置的 Recall 门槛”，以非零状态退出。
这是预期的质量检查失败；不是 Python 没有运行。k=2 也只有 0.75，仍过不了这个门槛。
