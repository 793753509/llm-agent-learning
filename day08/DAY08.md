# Day 08：给检索器出五道题，看它究竟错在哪里

> 今天先做一件事：不用模型，给 Day 05 的搜索程序批作业。
> 读完并跑通核心实验即可；向量对比和生成评估放在后半段。

## 1. 为什么前几天能回答，今天还要考试？

你问“周末几点关门”，程序找到周末营业时间，看起来很成功。
换成“WLAN 怎么用”，资料只写了 wifi，关键词搜索就可能找不到网络说明。

我们要知道的是：同一套程序，对一组固定问题分别表现怎样？
这组题叫**评估集**。每次修改代码，都用原来的题再跑一次，叫**回归评估**。

今天仍使用虚构的青禾自习室，资料就在 Day 05 的两个文件里。无需 API Key。

```text
题目：工作日和周末分别几点关门？
标准证据：hours.md#1 + hours.md#2
程序交卷：hours.md#1
批改：找到了一条，但没找全。
```

## 2. 先运行，再理解报告

从项目根目录运行：

```bash
uv run python -m day08.eval_retrieval --top-k 1
uv run python -m day08.eval_retrieval --top-k 2
```

`top-k` 表示最多取几条资料，沿用 Day 05 的意思。
程序会逐题打印“问题 → 找到的块”，再写入：

- `day08/reports/lexical-k1.json`
- `day08/reports/lexical-k2.json`

这些是程序实际计算的报告，不是预先填好的成绩。
使用仓库当前五道题和原文，已实跑的结果是：

| 配置 | 平均 Hit | 平均 Recall | MRR@k |
|---|---|---|---|
| k=1 | 0.75 | 0.625 | 0.75 |
| k=2 | 0.75 | 0.75 | 0.75 |

平均值只计算四道有答案题。R3 两次都没找到资料；R4 从找到一条变成找到两条。
所以 Recall 提高了，而 Hit 和 MRR 没变。改过资料或题目后，以你重新运行的结果为准。

## 3. 五道题长什么样？

打开 `day08/datasets/rag_cases.json`。

| 题号 | 问题 | 人工确认的证据 |
|---|---|---|
| R1 | 周末几点关门？ | hours.md#1 |
| R2 | wifi 免费吗？ | services.md#2 |
| R3 | WLAN 怎么用？ | services.md#2 |
| R4 | 工作日和周末分别几点关门？ | hours.md#1 和 hours.md#2 |
| R5 | 火星今天多少度？ | 没有 |

其中 R3 是换一种说法，R4 需要两条证据，R5 在资料里没有答案。
它们分别暴露同义表达、资料完整性和无答案处理的问题。

```json
{
  "id": "R4",
  "question": "工作日和周末分别几点关门？",
  "relevant_chunk_ids": ["hours.md#1", "hours.md#2"]
}
```

`relevant_chunk_ids` 是人读过资料后标的答案依据，不由被考试的检索器自己填写。
如果你改了资料或切块方式，编号可能改变，必须重新审核标注。
程序会检查标注的编号是否存在，但“存在”不能证明标注正确。

## 4. 手算三个数字

先不用背英文。设正确资料为 A、B，返回顺序为 C、A，只取前两条。

| 指标 | 问的事情 | 本题计算 |
|---|---|---|
| Hit@2 | 至少找到一条了吗？ | 找到 A，所以是 1 |
| Recall@2 | 应找的资料找回几成？ | 找到 1 条 / 应找 2 条 = 0.5 |
| RR@2 | 第一条正确资料排第几？ | A 在第 2 位，得 1/2 = 0.5 |

多道题的 RR 取平均，就是 MRR。我们的报告只看前 k 条，因此是 MRR@k。
三者都不是“模型回答正确的概率”。

再看代码最核心的两行：

```python
found = set(selected) & relevant
recall = len(found) / len(relevant)
```

- `set` 去掉重复编号。
- `&` 求交集，即“既在返回结果里、又在标准证据里”的编号。
- `len` 数个数。

A 出现两次不能冒充找回两条资料。RR 则要保留顺序，逐个看第几名首次命中。

**旧版教材中“前 k 条含任意正确资料”的公式实际是 Hit@k，已经更正。**

## 5. R5 为什么不能照着除？

R5 没有正确资料，分母会是 0。我们把它从 Hit/Recall/MRR 的平均值中移出，单独记录：

```text
returned_candidate_on_unanswerable = true / false
```

意思是“无答案题有没有被返回候选资料”。
关键词碰巧相同也可能返回候选，所以“有搜索结果”不等于“有答案”。
这也不等于模型错误作答：今天根本没有调用生成模型。

## 6. 怎样判断改动是否有帮助？

按这个顺序看 JSON：

1. `scope`：今天测的是关键词检索。
2. `top_k`：两份报告取几条是否一致？
3. `answerable_count`：平均分的分母是多少？
4. `cases`：究竟哪一道题变化了？
5. `mean`：最后再看总分。

k 变大通常更容易找到证据，也会让上下文更长、混入更多无关内容。
所以不能只宣布“Recall 提高了，系统就更好了”。

尝试设置一个严格门槛：

```bash
uv run python -m day08.eval_retrieval --top-k 1 --min-recall 1
```

这个实验应失败并提示未达门槛，因为 R4 在 k=1 时不可能找全。
命令失败在这里正是实验成功：你观察到了质量门槛拦住不达标结果。
`--min-recall` 是你设置的要求，不是行业统一标准。

## 7. 如果是回答错了，怎么排查？

以“周末 18:00 关门”为例：

| 看到的实际结果 | 先检查哪里 |
|---|---|
| 没找到 hours.md#1 | 检索：切块、措辞、排序、k |
| 找到了正确块，但 Prompt 没放进去 | 组装上下文：是否被长度限制丢掉 |
| Prompt 有 18:00，回答却写 21:00 | 生成：混淆资料、指令或模型能力 |
| 回答写 18:00，却引用 services.md#2 | 引用：编号存在，但证据不支持结论 |

引用格式正确，只能证明格式正确。不能用一个正则表达式证明事实正确。

想继续测生成时，在 Day 05 加 `--ask-model`，人工记录这四项：
“回答中的事实”“对应原文”“引用是否匹配”“资料不足时是否承认不知道”。
这一步会调用你配置的模型；本课离线报告没有包含它。
