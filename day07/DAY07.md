# Day 07：先选门店，再合并两种搜索的结果

> 今天用门店和错误码，学习过滤、混合检索、融合与重排。
> 先运行人工排名练习，再运行真实本地向量分支；默认不调用生成模型。

## 1. 为什么搜索相关还不够？

用户在北店看到 E101，想知道怎样处理。资料却有三种容易混淆的内容：

| 资料 | 含义 |
|---|---|
| 北店 E101 | 名额已满，选择其他时段 |
| 北店 E102 | 网络连接失败，切换网络 |
| 南店 E101 | 账号未验证，先验证手机号 |

单看“预约失败”或相似分数，可能拿错错误码或门店。
今天逐步解决：范围对不对、候选全不全、具体内容排得好不好。

## 2. 六块资料和排名从哪来？

| 文件或结果 | 来源与用途 |
|---|---|
| [knowledge.json](knowledge.json) | 人工编写的六条门店资料，已分块并填写 branch 标签 |
| [fusion_practice.py](fusion_practice.py) | 人工给定 A/B/C 排名，只练合并 |
| [hybrid_retriever.py](hybrid_retriever.py) | 真实执行过滤、两路检索和结果选择 |
| [fusion.py](fusion.py)、[reranker.py](reranker.py) | 合并排名、去重、字符预算和错误码规则 |
| 向量库与检索结果 | 在当前进程内创建，结束后释放；模型权重复用 Day 06 缓存 |

`north/booking.md#1` 是 JSON 中的逻辑来源标签，正文就在它的 `text` 字段，不需要另找一个 north/booking.md 文件。
这些资料不是 Day 05 原文自动升级出来的，是为今天的门店实验另写的一组数据。

## 3. 一条数据怎样经过各步骤？

```text
门店资料 → 先过滤北店 → 关键词排名 + 向量排名
                          ↓
                     RRF 合并排名
                          ↓
                  按完整错误码重排
                          ↓
              去掉重复原文，选出放得下的块 → Prompt
```

几个名字只需先记动作：

| 名称 | 本课意思 |
|---|---|
| metadata | 原文之外的标签，例如 `branch=north` |
| filter | 选出符合标签的资料 |
| lexical / vector | 按词字匹配 / 按向量相似程度搜索 |
| hybrid search | 组合两种检索方法 |
| fusion / rerank | 合并多个排名 / 再调整候选顺序 |

两路都使用过滤后的资料。`--branch north` 是你选的实验范围，不是登录认证；真实系统的访问范围应由服务端根据身份确定。

## 4. 先手算 RRF

两张**人工设计**的排名表：关键词 `[A,B]`，向量 `[B,C,A]`。
原始分数含义不同，本课不直接相加，而按排名给分：

```text
一条资料的 RRF 分数 = 它在各路的 1 / (60 + 排名) 之和
```

排名从 1 开始；没有出现在某路，该路贡献 0。

| 资料 | 关键词贡献 | 向量贡献 | 合计 |
|---|---|---|---|
| A | 1/61 | 1/63 | 约 0.032266 |
| B | 1/62 | 1/61 | 约 0.032522 |
| C | 0 | 1/62 | 约 0.016129 |

```bash
uv run python -m day07.fusion_practice
```

应看到 `B → A → C`。这里没有执行搜索，输入是提前写好的排名。
`rrf_fuse()` 按资料 ID 合并，所以 A 出现于两路会累加贡献，但最后仍只有一个候选。
常数与排名起点是本课约定，不能直接拿别的库默认分数逐项比对。[RRF 说明](https://qdrant.tech/documentation/search/hybrid-queries/#reciprocal-rank-fusion-rrf)

## 5. 再运行真实混合检索

从项目根目录运行；首次需要下载 Day 06 的模型：

```bash
uv run --group rag python -m day07.hybrid_retriever "E101 预约失败怎么办？" --branch north
```

观察输出里的六步：范围、两路排名、RRF、重排、去重、上下文选择。
当前资料的关键词路线会把 E102 和通用说明排得较高；向量路线也可能把通用说明排在前面。
RRF 合并这些意见，但它没有阅读内容来判断谁真正解释了 E101。

接着看规则重排：当前候选中包含 E101 的北店块应被放到前面。
这里的检索分数由程序和 Embedding 实算，具体小数以本次运行输出为准。

## 6. 重排究竟多做了什么？

`reranker.py` 从问题和原文提取完整错误码，把包含相同代码的候选排在前面；命中数量相同，再按 RRF 分数排列。

它不会修改 RRF 分数，所以重排后分数不一定从大到小。它也不会凭空找出没进入候选的资料。
这是范围明确的**规则重排**，没有训练过的重排模型；没有错误码时保留原排名。

```bash
uv run --group rag python -m day07.hybrid_retriever "E101 预约失败怎么办？" --top-k 1 --no-rerank
uv run --group rag python -m day07.hybrid_retriever "E101 预约失败怎么办？" --top-k 1
```

对照两次第一名和最终 input，看看规则是否补上了需要的具体说明。

## 7. 三个 k 和字符预算别混淆

| 参数 | 默认值 | 控制什么 |
|---|---|---|
| `--candidate-k` | 3 | 每一路最多取多少候选 |
| `--rrf-k` | 60 | 合并公式中的常数，不控制条数 |
| `--top-k` | 2 | 最终最多保留多少块 |
| `--max-chars` | 1200 | 组装后的 input 字符上限，不含独立 instructions |

每路最多三块，合并后可能少于六块，因为两路会找到相同资料。
之后按原文去重，并尝试逐块放入预算；放不下的块会被跳过，程序会打印它的 ID。

字符数不是 Token 数；预算过小可能跳过最重要的段落，不能只看检索排名，还要检查最终 input。

## 8. 再做两个小实验

```bash
uv run --group rag python -m day07.hybrid_retriever "E101 预约失败怎么办？" --candidate-k 1
uv run --group rag python -m day07.hybrid_retriever "E101 预约失败怎么办？" --branch south
```

第一条检查 E101 是否还进候选；如果两路都没找到，后续重排无法补救。
第二条应只搜索南店，E101 依据变成“先验证手机号”，不能夹带北店原文。

可再试 `--max-chars 1`，观察全部放不下时如何结束。
需要生成回答时另加 `--ask-model`，沿用 Day 03 配置；模型只收到最终选中的原文。

## 9. 真实项目里一般怎么做？

例如产品客服同时搜索型号、错误码和自然语言描述，关键词适合保留精确编号，向量帮助匹配不同措辞，再在少量候选上做重排。
关键词分支可用 BM25 等方法，重排也可用成对读取“问题与候选”的模型；是否改善，要用同一套业务问题比较。

大知识库通常提前建索引并持续更新。本课每次只编码当前门店的少量资料、建立内存库，是为了看清过滤；不会修改 Day 06 的持久化库。
