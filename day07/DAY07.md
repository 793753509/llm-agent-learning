# Day 07：两种搜索都找到了资料，最后该用哪一段？

> 今天的目标：先选对门店，再用两种方法找资料，把结果合并，最后把真正回答问题的段落放到前面。

继续用虚构的“青禾自习室”。今天增加北店、南店，以及两个预约错误码。所有规则都是教学资料，不对应真实业务。

第一次先读第 1～5 节，理解例子和运行结果；第二次读第 6～10 节，对照具体代码。BM25、模型重排、自动改写问题放到最后选读。

## 1. 一个向量分数解决不了所有问题

用户在北店预约时看到了 `E101`，问：

```text
E101 预约失败怎么办？
```

我们有这些资料：

| 来源 | 门店 | 原文 |
| --- | --- | --- |
| `north/booking.md#1` | 北店 | 北店 E101 表示预约名额已满。请选择其他时段。 |
| `north/booking.md#2` | 北店 | 北店 E102 表示网络连接失败。请切换网络后重新预约。 |
| `north/help.md#1` | 北店 | 北店预约失败时，请查看页面提示的错误编号，再联系前台。 |
| `north/network.md#1` | 北店 | 北店 wifi 免费，连接方式请咨询前台。 |
| `south/booking.md#1` | 南店 | 南店 E101 表示账号未完成验证。请先验证手机号。 |
| `south/network.md#1` | 南店 | 南店 wifi 每小时 5 元，连接方式请咨询前台。 |

我们要找的是第一段。

但你可以看出几个陷阱：

- “预约失败通用说明”与问题很接近，却没有解释 `E101`。
- `E101` 和 `E102` 只差一个数字，处理方法却不同。
- 南店也有 `E101`，但原因和北店不同。

**相关、编号正确、业务范围正确，是几件需要分别检查的事。** 今天的每一步都在解决其中一个问题。

## 2. 先把几个新名字翻译成人话

| 名字 | 今天实际做什么 |
| --- | --- |
| Metadata，元数据 | 给资料贴标签，例如 `branch="north"` 表示北店 |
| Filter，过滤 | 先选出北店的资料 |
| Recall，召回 | 搜出一批可能有用的候选段落；这里不是 Day 08 的指标公式 |
| Hybrid Search，混合检索 | 用关键词和向量两种方法分别搜索 |
| Fusion，融合 | 把两张排名表合成一张，重复的资料只保留一份 |
| RRF | 一种根据“排名”计算合并分数的方法 |
| Rerank，重排 | 对候选再检查一次，调整先后顺序 |
| 最终 top-k | 最后最多把几段原文交给生成模型 |

先不用背英文，记住本课的数据流：

```text
六条门店资料
    ↓ 按 branch 过滤
北店四条资料
    ├─ 关键词检索 → 最多三条候选
    └─ 向量检索   → 最多三条候选
                      ↓
                 按来源 ID 合并
                      ↓
                 检查完整错误码，重排
                      ↓
                 去重、检查输入长度
                      ↓
                 最多两段原文 → 模型输入
```

两种搜索方法可能各自找到对方漏掉的资料，所以先让它们都给出候选。但混合检索没有“必然更准”的保证，需要看实际结果。

## 3. 第一步：门店标签比“相似”更明确

资料现在放在 [knowledge.json](knowledge.json)。其中一条长这样：

```json
{
  "id": "north/booking.md#1",
  "source": "north/booking.md",
  "index": 1,
  "branch": "north",
  "text": "北店 E101 表示预约名额已满。请选择其他时段。"
}
```

`text` 是原文，`branch` 是我们明确填写的门店标签。这个标签是 metadata，不是模型猜出来的，也不是向量中的某一维。

本课数据直接写成已经分好的六条记录，方便观察过滤。`source` 是资料的逻辑来源标签，实际原文存在这份 JSON 中；没有要求你再创建对应的六个 Markdown 文件。

过滤的核心是普通 `if`：

```python
# load_branch_chunks() 的核心逻辑示意。
for record in records:
    if record["branch"] == "north":
        # 把这条资料转换为 Chunk，加入待搜索列表。
        ...
```

这一步完成后，关键词和向量两路都只搜索北店资料。我们在 Python 中先做过滤，再建立本次演示用的内存向量库；没有把其他门店交给生成模型后再要求它忽略。

`--branch north` 是练习中指定查询范围的参数，**并不是真实的权限验证**。它可以由你手动改成 south；实际多租户系统应由服务端根据登录身份确定可访问范围，再同时限制所有检索路线。

## 4. 先做一个不用模型的小实验：两张名单怎么合并？

假设两种检索器返回了下面的排名。A、B、C 只是三个资料编号，这是一组人工设计的排名，不是模型实测：

```text
关键词：第 1 名 A，第 2 名 B
向量：  第 1 名 B，第 2 名 C，第 3 名 A
```

不能直接把两路原始分数相加：Day 05 的分数是“共同词/字占比”，Day 06 的分数是“向量的余弦相似度”，含义不同。

RRF 先不看那些原始分数，只看每段资料在各路排第几。本课约定：

```text
每路贡献 = 1 / (60 + 排名)
总分 = 这段资料从各路获得的贡献相加
```

本课排名从 1 开始，60 叫 `rrf_k`。它用于控制排名贡献的差异，**不是最后返回多少段的 top-k**。

手算：

| 资料 | 关键词贡献 | 向量贡献 | 合计 |
| --- | --- | --- | --- |
| A | `1 / 61` | `1 / 63` | 约 0.032266 |
| B | `1 / 62` | `1 / 61` | 约 0.032522 |
| C | 0，没出现在这一路 | `1 / 62` | 约 0.016129 |

所以合并顺序是 `B → A → C`。B 在两路都比较靠前，合计得分最高。

在项目根目录运行：

```bash
uv run python -m day07.fusion_practice
```

应看到：

```text
B: 0.032522 排名={'关键词': 2, '向量': 1}
A: 0.032266 排名={'关键词': 1, '向量': 3}
C: 0.016129 排名={'向量': 2}
```

这一步不用安装模型，也不请求任何 API。[fusion_practice.py](fusion_practice.py) 故意把原始分数都填成零，证明 RRF 只读取列表排名。

本课自己实现 RRF，便于逐行理解。其他库可能使用不同的默认常数或从 0 开始的排名，因此不能把它们的分数直接拿来逐项对照。[Qdrant 的 RRF 说明](https://qdrant.tech/documentation/search/hybrid-queries/#reciprocal-rank-fusion-rrf)

### 5.2 看一份实际运行的排名

以下来自本课的一次真实运行。模型数值可能有细微差异；先核对来源和每一步的变化。

| 阶段 | 第 1 名 | 第 2 名 | 第 3 名 |
| --- | --- | --- | --- |
| 关键词 | E102 网络失败，0.500 | 预约失败通用说明，0.500 | E101 名额已满，0.375 |
| 向量 | 预约失败通用说明，约 0.630 | E101 名额已满，约 0.604 | E102 网络失败，约 0.604 |
| RRF 合并 | 预约失败通用说明 | E102 网络失败 | E101 名额已满 |
| 完整错误码重排 | **E101 名额已满** | 预约失败通用说明 | E102 网络失败 |

向量分数打印时只保留三位小数，显示相同的 `0.604` 不代表内部完整分数相同。

RRF 把两路意见合并，却没有阅读内容来判断哪个段落真正解释了 `E101`，所以还需要下一步。

## 6. 看源码：RRF 为什么不会把一段资料保存两份？

打开 [fusion.py](fusion.py)，先看 `Candidate`：

```python
@dataclass
class Candidate:
    chunk: Chunk
    rrf_score: float = 0.0
    ranks: dict[str, int] = field(default_factory=dict)
```

它保存一段原文、合并分数，以及这段资料在各路的排名。`default_factory=dict` 表示每个候选都有自己的排名字典。

`rrf_fuse()` 内部有一个字典 `merged`，键是资料 ID：

```python
# 源码节选，放在遍历检索结果的循环中。
if chunk_id not in merged:
    merged[chunk_id] = Candidate(chunk=result.chunk)
candidate = merged[chunk_id]
candidate.rrf_score += 1 / (rrf_k + rank)
candidate.ranks[route] = rank
```

如果两路都找到 `north/booking.md#1`，它们更新的是同一个字典条目。因此最后只有一份原文，但记录了两路的排名贡献。

代码还用 `seen` 集合跳过同一路里的重复 ID，避免同一检索器重复返回一段资料时让它多得分。

同分时按来源 ID 排序，便于重复运行和核对。本课这种稳定顺序是可重复的约定，不代表同分时某个 ID 天生更相关。

**一个限制：没出现在任何一路候选里的资料，RRF 无法凭空找出来。**

## 7. Rerank：对候选再检查一次

本课先写一个能解释清楚的规则：

> 用户问了一个完整错误码，就优先排列包含同一个完整错误码的候选。

例如问题里的 `E101`：

- “北店 E101 表示名额已满”命中完整编号。
- “北店 E102 表示网络失败”没有命中。
- “北店预约失败时……”也没有命中。

[reranker.py](reranker.py) 会提取类似 E101 的完整编号，再比较：

```python
# rerank() 中的源码节选。
query_codes = extract_codes(query)


def priority(candidate: Candidate) -> tuple[int, float]:
    matches = query_codes & extract_codes(candidate.chunk.text)
    return len(matches), candidate.rrf_score


return sorted(candidates, key=priority, reverse=True)
```

这里又用到了 Day 05 的集合交集 `&`。

排序依据是两个数：先比完整错误码命中数量，命中数量相同时，再比 RRF 分数。因此 E101 资料即使 RRF 分数略低，也能被移到第一。

程序会打印每条候选命中了哪些编号。重排不会修改原来的 `rrf_score`，所以重排后的列表不必按 RRF 分数递减。

**这是教学用规则重排，不是训练过的 Cross Encoder，也不是通用的语义判断器。** 没有错误码的问题不会触发这种优先级；包含正确编号的文章也不一定真的包含答案。

Cross Encoder 是另一种常见重排方法：把“问题 + 一段候选原文”一起交给模型打分，再按新分数排序。它和先分别生成向量、再比较向量的做法不同。通常先检索少量候选，再做这种成对计算。[Sentence Transformers 的说明](https://www.sbert.net/docs/quickstart.html#cross-encoder)

今天先看懂规则如何改变排名，模型重排留到扩展练习。

## 8. 分清三个 k，避免参数一改就混乱

| 参数 | 本课默认值 | 控制什么 |
| --- | --- | --- |
| `--candidate-k` | 3 | 每一路最多取多少候选 |
| `--rrf-k` | 60 | RRF 分数公式中的常数 |
| `--top-k` | 2 | 最后最多给生成模型几段资料 |

例如：

```bash
uv run --group rag python -m day07.hybrid_retriever --candidate-k 3 --top-k 1
```

不是只找一条资料。它先让每一路最多找三条，合并、重排后再选择一条。

一条资料可能同时被两路找到，所以“每路三条”合并后不一定有六条。

如果一开始只让每路找一条，正确的 E101 资料可能根本进不了候选。后面的规则再好，也无法把没见过的段落提上来。

## 9. 排好名后，还要控制交给模型的内容

### 9.1 两种去重做的事情不同

RRF 按 ID 合并：同一个来源编号只出现一次。

`deduplicate_text()` 再按原文合并：如果不同 ID 的原文去掉多余空白后完全一样，只保留排名靠前的一份。它不判断“措辞不同但意思相近”的段落，也不会合并彼此冲突的内容。

这是为了避免重复原文占据最终 top-k。需要保留所有重复来源时，应再增加来源集合；本课只保留第一份的来源。

### 9.2 先用字符预算看清楚输入长度

本课参数 `--max-chars 1200` 限制整个 `input` 字符数，包括问题、资料、来源编号和分隔文字，不包括单独的 instructions。

**字符数不等于模型 Token 数。** 这里用它做容易观察的练习，没有声称实现了精确 Token 计费或完整上下文窗口管理。

`select_context()` 逐条尝试加入完整段落：

```python
if len(build_prompt(query, selected + [result])) > max_chars:
    skipped.append(candidate.chunk.id)
    continue
selected.append(result)
```

`selected + [result]` 是“假如再加入这一段”的临时列表。只有拼出来的输入没有超出预算，才真正加入 `selected`。

放不下时会跳过该块并打印它的 ID，继续尝试后面的候选；这意味着很小的预算可能跳过最有用的长段落。它不会把段落随意截成半句话。

所有候选都放不下时，程序不发送空资料去请求生成模型。

默认例子的一次运行最终选择了：

```text
[来源: north/booking.md#1]
北店 E101 表示预约名额已满。请选择其他时段。

[来源: north/help.md#1]
北店预约失败时，请查看页面提示的错误编号，再联系前台。
```

本次 `input` 共 135 个字符，以实际打印为准。来源随原文一起进入 Prompt；仅在更早的检索日志里出现、最终没被选中的来源，不应出现在答案引用里。

## 10. 按函数串起来读一遍

打开 [hybrid_retriever.py](hybrid_retriever.py) 的 `main()`：

| 步骤 | 函数 | 输入 → 输出 |
| --- | --- | --- |
| 门店过滤 | `load_branch_chunks()` | 门店标签 → 当前门店的 chunks |
| 关键词 | Day 05 的 `retrieve()` | 问题和 chunks → 字面匹配结果 |
| 向量 | Day 06 的编码、建库和 `search_vectors()` | 同一批 chunks 与问题 → 向量结果 |
| 合并 | `rrf_fuse()` | 两张排名表 → 一张候选表 |
| 重排 | `rerank()` | 问题和候选表 → 调整顺序后的候选 |
| 去重 | `deduplicate_text()` | 候选 → 无完全重复原文的候选 |
| 选择输入 | `select_context()` | 候选、段数、字符预算 → 最终段落 |
| 拼接输入 | Day 05 的 `build_prompt()` | 问题和最终段落 → input 字符串 |

关键词分数、向量分数、RRF 分数各有各的含义。我们保留它们的轨迹，是为了知道排名在哪一步改变，不是要把所有分数再加一遍。

## 11. 三个必做小实验

### 实验一：关闭重排，会有什么区别？

```bash
uv run --group rag python -m day07.hybrid_retriever --top-k 1 --no-rerank

```

对照第 4 步排名和最终 input。默认资料的一次实测中，关闭重排后选的是通用说明，开启后选的是 E101 的具体处理办法。

如果你改过原文导致顺序不同，也以实际结果为准。要能解释变化原因，不要为了对上文档而修改分数。

### 实验二：候选太少，重排能救回来吗？

```bash
uv run --group rag python -m day07.hybrid_retriever --candidate-k 1 --top-k 1
```

检查 E101 资料是否出现在第 2a、2b 步。如果两路都没选到它，后面的 RRF 和重排都无法补回。

恢复 `--candidate-k 3` 再比较。这就是“先尽量找到候选，再从候选里选好结果”的含义。

### 实验三：只换门店，结果会怎样？

```bash
uv run --group rag python -m day07.hybrid_retriever "E101 预约失败怎么办？" --branch south --top-k 1
```

第 1 步应该只留下南店两条资料；后续两路候选和最终 input 中都不应出现北店原文。E101 对应的处理应变成“先验证手机号”。

再试 `--branch north`，确认同一个错误码在不同门店的数据范围里得到不同依据。

完成后可以额外试一次 `--max-chars 1`，观察所有段落都放不下时程序如何结束；这只检查预算分支，不用于评价检索质量。

## 12. 常见错误：先定位哪一步出问题

| 问题 | 先检查什么 |
| --- | --- |
| 最后引用了其他门店 | 两路检索是否都使用过滤后的资料？ |
| 正确段落完全没出现 | 原文是否在当前范围、候选数是否过小？ |
| 两路都找到同一段，却重复占两个位置 | 是否按 chunk ID 合并？ |
| RRF 第一名还是不能回答 | 融合只结合排名，检查内容重排是否必要 |
| E101 和 E102 混在一起 | 是否比较了完整编号，不能只匹配数字的一部分？ |
| 重排后第一名 RRF 分数反而小 | 本课重排先看编号命中，这是预期行为 |
| 排第一的资料没有进入 input | 查看去重和字符预算，是否被跳过？ |
| 生成模型引用了未提供的来源 | 回查最终 input；提示词要求引用正确不等于自动验证通过 |

这里默认不自动证明最终回答正确。即使完整错误码命中了，也要阅读原文，确认它支持回答中的结论。

## 13. 扩展阅读：主线学会后再加

### BM25：更成熟的关键词打分

Day 05 只是数共同词/字。BM25 还考虑词在当前文档中出现的频率、这个词在整个知识库里是否常见，以及文档长度等因素。

先保留当前实现方便手算，之后再替换关键词一路。中文仍要处理分词，完整错误码应尽量保留成一个单位。今天不需要先安装 `rank-bm25` 才能运行主线。

### 模型重排：让模型成对阅读问题和候选

可以把本课 `rerank()` 替换为 Cross Encoder 或 Rerank API。入口仍然是“问题 + 少量候选原文”，输出仍然是新的顺序。

它会增加计算或请求成本，也可能排错。用同一批问题比较是否更好；不要对整个知识库的每一段都做昂贵的成对打分。

### Query Rewrite：把“那怎么办”补成独立问题

例如上一轮说“我在北店预约，提示 E101”，这一轮问“那怎么办？”。只用“那怎么办”搜索会缺少门店和编号。

有了明确对话上下文，可以把检索问题补成：

```text
原问题：那怎么办？
已有上下文：北店、预约、E101
用于检索的问题：北店预约提示 E101 应该怎么处理？
```

这只能补上已知信息，不能把 E101 猜成 E102，也不能凭空补一个门店。本课入口没有自动多轮改写；你可以先手工比较这两个问题的检索结果。

以后实现时保留原问题和改写结果，记录两者；在需要时保留原问题的检索路线，防止改写改变意图。涉及权限的范围仍由可信身份确定，不能交给改写模型猜。
