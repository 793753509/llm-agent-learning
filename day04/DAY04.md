# Day 04：把“刚才的结果”带进下一轮

> 今天看清 session、history、turn 三个变量，让两次用户提问接得起来。
> 参考程序会调用真实模型；历史存在本地内存，退出后不再保留。

## 1. 为什么第二次提问需要历史？

你先问“精确计算 25 乘 3”，再问“把结果再乘 5”。第二句没有写 75，应用必须提供上一轮内容，模型才能知道“结果”指什么。

这里的一轮（turn）是**一次用户提问到最终回答的全过程**，可能包含多次模型请求与工具结果。

```text
用户第 1 轮：25×3 → 模型请求工具 → 工具返回75 → 模型回答75
用户第 2 轮：把结果乘5 → 携带第1轮历史 → 工具返回375 → 模型回答375
```

## 3. 连续问两次，再清空

在项目根目录运行，使用 Day 03 的配置：

```bash
uv run python -m day04.chat_agent
```

在同一进程中依次输入：

```text
精确计算 25 乘 3
把结果再乘 5
/history
/usage
/reset
/history
/quit
```

前两题应能观察到 75、375 的工具结果；具体回答措辞由模型生成。
`/reset` 后历史为空，用量计数也重置，但已经消耗的服务额度不会退回。

## 4. 三个列表各存什么？

| 变量 | 内容 | 什么时候创建 |
|---|---|---|
| `session.turns` | 多个已完成轮次，每轮又是一个列表 | 进入聊天循环之前 |
| `history` | 把旧轮次展开成一个列表 | 每次进入 `chat()` |
| `turn` | 当前用户问题、本轮模型输出、工具结果 | 每次进入 `chat()`，从空的新轮次开始 |

在 `chat()` 中找到：

```python
history = []
for previous_turn in session.turns:
    history.extend(previous_turn)
turn = [{"role": "user", "content": question.strip()}]
```

请求模型时用 `history + turn`，也就是旧历史加本次进展。
结束时只保存本轮 `turn`，不要把 `history + turn` 整份再保存一次，否则旧历史会不断重复。

## 5. append、extend、+ 用一个例子记

```python
turns = []
turns.append(["用户问", "模型答"])
# turns = [["用户问", "模型答"]]：把完整一轮作为一项。

history = []
history.extend(turns[0])
# history = ["用户问", "模型答"]：把轮次中的各项展开。

request = history + ["用户追问"]
# 创建新列表，history 本身没有增加“用户追问”。
```

真实列表中保存的是消息对象或字典，上面的字符串只为解释形状。
Python 写法可以查 [Day 03 速查](../day03/PYTHON_REFERENCE.md)。

## 6. 两层循环在哪里结束？

外层 `chat_loop()` 不断收用户问题，同一个 session 一直保留。
内层 `chat()` 反复请求模型、执行工具，直到拿到最终回答。

```text
chat_loop：问一次 → chat → 显示回答 → 再问一次
chat：请求模型 → 有工具就执行并继续 → 无工具且有回答就保存本轮并返回
```

参考版通过 Day 03 的 `reply.output_items` 保留完整模型输出。
个人练习直接操作 SDK，用 `item.to_dict(mode="json")` 转成字典；两种写法都需保留工具调用、关联 `call_id` 和其他输出项。

只有本轮完成后才 `session.turns.append(turn)`。参考版最多保留五个完整轮次，删除时整轮删除，避免留下孤立的工具结果；五轮只是教学限制，不是精确 Token 预算。
请求失败时当前轮不保存，但此前已发生的模型请求仍可能产生用量。

## 7. 按七步检查个人练习

打开 `agent_practice.py` 中的 TODO 标记，把它们当作检查点：

1. 计算器正确处理允许的运算。
2. 展开旧 history，创建只含本次问题的 turn。
3. 发送 `history + turn` 与工具说明。
4. 保存完整模型输出，找出工具请求。
5. 无工具调用时保存完整轮次并返回回答。
6. 有工具时实际执行，将结果绑定原 `call_id`，继续循环。
7. 外层持续使用同一个 session 调用 chat。

运行个人练习：

```bash
uv run python -m day04.agent_practice
```

验收顺序仍用“25×3 → 再乘5 → /history → /reset”。参考入口和练习入口是两个独立进程，历史不会共享。

## 8. 选做：为什么 JSON 看起来对，仍需要校验？

在参考程序里输入：

```text
/plan Python 列表
```

程序请模型输出包含 `topic`、`tasks` 的 JSON，然后执行：

```python
plan = StudyPlan.model_validate(json.loads(answer))
```

`json.loads()` 检查是否是合法 JSON；Pydantic 按 `StudyPlan` 校验字段与约束，例如任务时长 5～240 分钟。
本课用普通文本请求再本地校验，没有启用服务端严格结构化输出，校验失败是可能发生的。
格式通过也不代表学习计划合理，仍要阅读内容。

## 9. 真实项目里一般怎么做？

聊天应用通常用会话编号找到用户历史，选择本次需要的内容，再发给模型。历史可能存在数据库或由支持会话状态的服务管理；无论存在哪，都要明确怎样关联当前请求。[会话状态说明](https://developers.openai.com/api/docs/guides/conversation-state)

长聊天会采用长度预算或摘要，并保留完整工具调用关系。用户偏好和业务知识另行管理，避免把所有数据都塞进聊天历史；Day 11、13 会讲这几个存储用途的区别。

## 10. 自测与完成标准

1. 一轮用户提问为什么可能请求模型两次？
2. session 若在外层循环里每次重新创建，会怎样？
3. 历史有十条消息，能否随便删最早三条？

<details>
<summary>参考答案</summary>

1. 第一次提出工具请求，第二次读取工具结果并生成回答。
2. 上一轮历史丢失，追问缺少上下文。
3. 不能随意拆散工具请求与结果，本课按完整轮次裁剪。

</details>

能解释三个列表、跟踪一次追问、观察重置效果，就完成核心课；学习计划校验可后做。
