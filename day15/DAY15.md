# Day 15：助手变慢了，先查它在哪一步花了时间

> 今天给一次请求贴上编号，记录检索与工具步骤，亲眼看到一条失败记录。
> 只写本地 JSONL 日志；费用计算使用明确标注的假设数据。

| 内容 | 来源与用途 |

## 1. “出错了”这三个字为什么不够？

你看到用户等了很久。可能是读取资料慢，也可能是工具超时，还可能是模型迟迟没返回。
只有最终答案或一个笼统报错，无法区分这些情况。

我们给完整请求一个 `trace_id`，给每个步骤一个 `span_id`。
像快递单一样：trace_id 标识整单，span_id 标识其中某一段运输。

```text
trace_id = abc
  span 1：retrieve，开始 → 结束，用时 2ms
  span 2：tool，开始 → 超时，用时 20ms
```

上面的毫秒数只是示意，真实时间由程序在你的机器上测量。

## 2. 运行成功和失败两个版本

```bash
uv run python -m day15.tracing
uv run python -m day15.tracing --fail
```

输出会告诉你本次日志文件路径，并打印文件内容。
文件在 `day15/logs/随机编号.jsonl`，每次新建一份，目录不提交。

第一条有 retrieve、tool 各自的 start/end。
第二条把工具换成“立即抛出 TimeoutError”的故障演示，有 start/error。
它没有真的等待网络超时，因此不要把这个故障时长当作网络性能。

## 3. 一行日志逐字段读

```json
{
  "trace_id":"abc",
  "span_id":"def",
  "stage":"tool",
  "event":"error",
  "error_type":"TimeoutError",
  "duration_ms":0.12
}
```

这是为了方便阅读拆开的示意。实际 JSONL 每行是一个完整 JSON 对象。

| 字段 | 你拿它回答什么问题 |
|---|---|
| trace_id | 哪一整次请求？ |
| span_id | 哪一个具体步骤？ |
| stage | 检索、工具还是回答？ |
| event | 开始、结束还是失败？ |
| error_type | 哪类异常？ |
| duration_ms | 这一段经过多少毫秒？ |

同一 span 的 start/end 使用相同编号，才能配对。
跨步骤用 trace_id 串起来，才能把一次请求完整找回。

## 4. with trace.span 为什么能自动计时？

```python
with trace.span("retrieve"):
    chunks = split_documents(load_documents(KNOWLEDGE_DIR))
    results = retrieve("周末几点关门？", chunks)
```

进入 with：记开始时间、写 start。
执行块内代码；离开 with：算时间差、写 end。
如果块内抛异常：写 error，再把异常继续抛给上层。

`@contextmanager` 帮我们把这套“进入/离开”逻辑包装起来。
里面的 `yield` 是暂停在这里，让 with 中间的业务代码先运行。

计时用 `time.perf_counter()`，适合算时间差。
`(结束 - 开始) * 1000` 把秒换成毫秒。

## 5. 为什么没有把整个问题和异常原文写进去？

本例日志只写允许的结构字段。异常只记类型，不直接记 `str(exc)`。
因为真实问题、工具参数、异常文本可能包含工单正文、凭证或 URL 参数。

阶段名也只允许 retrieve/tool/answer/workflow，避免误把用户问题当名称写入。
这不是完整日志平台，仍可以根据需要加“候选数量、模型名、重试次数”等经过审核的字段。

注意代码有文件路径才能继续排查；本例控制台会给你该路径。
不要把“减少敏感原文”理解成“什么诊断信息都不留”。

## 6. Token 怎样换算费用？先算一道假设题

假设某服务的单价为：

```text
输入：每百万 token 2 元
输出：每百万 token 6 元
本次：输入 1000 token，输出 200 token
```

那么：

```text
1000 / 1000000 × 2 + 200 / 1000000 × 6 = 0.0032 元
```

程序末尾打印这个结果。**这是数学练习，不是当前任何服务商的报价，也不是本次真实账单。**

```python
estimated_cost({"input_tokens": 1000, "output_tokens": 200}, 2, 6)
```

模型真正返回 usage 时，才有本次真实计数。一次任务调用三次模型，应汇总三次，不能只看最后一条。
本课没有模型调用，模型调用数为 0；没有采集的 usage 用 None 表达。
“未知”不能装成“已测量为零”。

## 7. 哪些费用今天没有算？

这段函数只算输入和输出两种单价。
缓存输入、推理 token、工具服务费用、Embedding、税费等规则依服务而定，需要读该服务的实际账单定义。
如果某类 token 已包含在输出总数里，不可再重复加一次。

先检查单位：人民币还是美元？每千还是每百万？
不要把 Python 的字符长度 `len(text)` 当作准确 token 数。

## 8. 从一条日志到一次排查

假设答复慢了：

1. 根据 request_id/trace_id 找到这一请求。
2. 看有没有 error，先处理明确失败。
3. 比较各阶段的 duration_ms，找花时间最多的位置。
4. 若模型阶段慢，再区分首个输出的等待和完整生成的等待。
5. 改一处后重跑相同样例，比较结果与时间。

本例没有采集首 token 延迟，也没有嵌套 span 的父子关系。
并发阶段的时长不能直接求和当整单时长；整单需要另设外层计时。

## 真实场景里怎么用

真实服务常把同一请求的模型、检索和工具记录关联起来，按编号查慢在哪一步。可以先保留步骤、时长、错误类型和必要用量，再接集中日志或追踪平台；平台不会自动替你判断哪些业务步骤应该记录。
