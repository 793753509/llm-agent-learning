# Day 17：资料员、审核员、写作者，怎样交接才有用？

> 今天先用三个普通函数演示角色交接，亲眼看到“坏证据被退回”。
> 这是确定性流程实验，没有悄悄启动三个模型，也不声称它已经是自主多 Agent 系统。

## 开始前：输入、程序和产物

| 内容 | 来源与用途 |
|---|---|
| [roles.py](roles.py) | 课程提供的资料员、审核员、写作者三个函数 |
| 证据原文 | 从 Day 05 的 knowledge 文件实际读取 |
| Evidence、Review、output | 函数运行时产生并打印；--tamper 故意修改其中的摘录，不改原始资料 |

## 1. 从一个分工问题出发

有人问青禾自习室：“周末几点关门？”
你可以让一个助手直接查资料回答，也可以分工：

```text
资料员：找原文并带上来源编号
审核员：核对编号与摘录
写作者：把通过检查的摘录展示出来
```

分工是否值得，取决于它有没有减少错误。
这个小问题通常一个检索流程就够了。今天拆开，是为了学会数据交接和职责边界。

## 2. 先看正常版和被篡改版

```bash
uv run python -m day17.roles
uv run python -m day17.roles --tamper
```

正常版应出现：

```text
evidence：hours.md#1 的原文
review.approved：true
output：资料摘录 + 来源
```

篡改版把摘录改成“周末通宵开放”，仍挂着原来的来源编号。
审核员对照真实文件，发现内容不一致，输出“停止：引用编号或原文不匹配”。

这展示了一个实际收益：来源编号不能给任意编造的文字作证明。

## 3. 角色不是三个名称，而是三个不同的输入输出

| 角色函数 | 输入 | 输出 | 不越过的边界 |
|---|---|---|---|
| research | 问题 | Evidence 列表 | 只提供候选原文 |
| review | Evidence 列表 | 是否通过、原因 | 不自行编写业务事实 |
| write | 已通过的 Evidence | 带来源的摘录 | 不改写出新事实 |

这里的关键是输入输出约定。没有约定，只让三个人聊天，很难知道下一步该接什么。

## 4. 交接包长什么样？

```python
class Evidence(BaseModel):
    source_id: str
    quote: str
```

例如：

```json
{
  "source_id":"hours.md#1",
  "quote":"## 周末开放时间\n周末开放时间为 09:00—18:00，18:00 关门。"
}
```

`source_id` 让审核员知道去哪核对，`quote` 是实际看到的文字。
如果只交接“我已经研究过了，答案是 18 点”，下一位很难独立检查。

Review 则包含 approved 和 reason。
下游读明确的布尔字段，不靠搜索一句自然语言里有没有“通过”两个字。

## 5. 审核员今天到底检查了什么？

```python
item.source_id in source
item.quote == source[item.source_id]
```

第一行检查编号存在；第二行检查摘录与原文完全一致。
这是很窄、可自动确认的规则。

**它没有判断这份原文是否回答了当前问题。**
例如问火星温度，碰巧搜到预约资料，编号和摘录可能都真实，但答非所问。
因此程序把输出标成“资料摘录”，并在审核理由中注明尚未验证问题相关性。

不要把一个名叫 reviewer 的函数理解成无所不知的事实审查员。

## 6. Handoff、Router、Supervisor 怎么区分？

不用今天就实现三个框架，先对应业务动作：

| 名称 | 青禾例子 | 关注点 |
|---|---|---|
| Router | 看问题属于资料查询还是工单查询 | 开头选哪条路 |
| Handoff | 资料员把带来源的包交给审核员 | 谁把什么交给谁 |
| Supervisor | 负责人决定继续查、交写作者还是停止 | 持续分配任务与收尾 |

今天 `run()` 用固定顺序做一次 handoff，没有让模型动态挑选下一位，也没有 supervisor 循环。

## 7. 真正接多个 Agent 时，增加的是什么？

可以把某个角色函数内部换成模型调用，给它专门的指令和有限工具。
例如资料员只能搜索，写作者只能读审核通过的证据。
多个角色可以使用相同模型；“多 Agent”不等于必须用三种不同品牌的模型。

新增成本也很具体：多次请求的费用、等待时间、重复资料、互相矛盾的输出、失败重试。
只有当角色独立验证或专门工具带来的收益超过这些成本，分工才划算。

一个 Agent 调用三个普通工具，也不自动变成三个 Agent。
本课的三个函数用于看清交接原理，不冒充真实模型评估结果。

## 8. 审核失败后应该一直重做吗？

今天直接停止。这样容易看出哪里出错，也不会悄悄无限循环。
可以进阶增加“最多重新检索一次”，但要把次数放进状态：

```text
审核失败且 retry_count=0 → 重新查一次
再次失败 → 停止并解释缺什么证据
```

“让两个 Agent 讨论到满意为止”没有具体终止条件，可能一直消耗请求。
预算应包含次数、时间、token，以及谁可以宣布完成。
